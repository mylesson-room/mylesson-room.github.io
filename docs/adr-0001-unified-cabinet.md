# ADR 0001 — Единый эталон кабинета GoStudy

Статус: направление согласовано, код и данные пока не мигрированы. 2026-11-18.

## Решение
- Один визуальный эталон — кабинет Михаила: student-business-ai-finance.html.
- English Placement — второй контрольный сценарий, а не второй визуальный эталон.
- Общие компоненты кабинета, словаря, чата, назначений, урока, домашки и мобильной верстки должны иметь один источник реализации.
- Отличаются только профиль и данные, права, назначенные уроки, прогресс, а также явно заданные типы занятий (у диагностики может не быть домашки).
- Целевой единый маршрут ученика будет загружать назначения из Supabase Auth + RLS. Старые student-*.html сохраняются как совместимые ссылки до проверенного перехода.
- Запрещается создавать новые персональные HTML кабинеты: ученик — запись/назначение, а не отдельная страница.
- Экспериментальные функции Михаила не переносятся автоматически без согласования.

## Факты read-only аудита 2026-11-18
- В текущем репозитории 18 файлов student-*.html.
- Обе тестовые страницы используют gostudy-v1-cabinet.js и gostudy-v1-cabinet.css, но различаются шрифтами, механизмом входа и учётом выученных слов.
- Supabase: finance_events — 183, classroom_events — 558, classroom_rooms — 6, progress — 46, private_lessons — 2.
- У private_lessons единственный PK — slug. Это препятствие для повторного использования одной записи slug на разных учеников.
- Таблицы homework_assignments, homework_published и vocabulary_items пока пусты, но реальные записи могут находиться в legacy events или localStorage.
- RLS включён; отдельные SECURITY DEFINER функции требуют аудита по Supabase Security Advisor.

## Целевые понятия
- profile: пользователь и роли teacher/student.
- lesson: многократно используемый учебный материал (не отдельный HTML-файл ученика).
- student_lesson_assignment: связь student_id + lesson_id + статус публикации и доступ.
- classroom: конкретная комната учитель–ученик; event/answer/chat привязан к комнате.
- vocabulary: записи ученика с правами на просмотр назначенным преподавателем.
- homework: черновик преподавателя, назначение, публикация, попытка и обратная связь.

## Этапы и запреты
1. Зафиксировать безопасную исходную версию и выполнить проверяемый backup БД перед DDL или переносом данных.
2. Составить реестр существующих таблиц, записей, RLS, событий и старых ссылок.
3. Определить целевую схему без параллельных таблиц там, где можно переиспользовать существующие; подготовить идемпотентную миграцию с откатом.
4. Объединить auth/session/access; затем общий рендерер кабинета; затем shared vocab/chat/answers/homework.
5. Перенести Михаила и Placement, проверить роли, сохранение данных, desktop/mobile и прямые ссылки.
6. После приёмки распространить на других; публикация только по явному «Согласовано».

НЕЛЬЗЯ: удалять старые страницы, таблицы, реальные слова/ответы, менять production main или выполнять SQL INSERT/UPDATE/DELETE/DDL без плана миграции. Нельзя помещать персональные данные и секреты в репозиторий.

## Критерий готовности
При одинаковом разрешении оба кабинета одинаковы по общему интерфейсу. Разные пользователи имеют изолированные назначения, словари, чаты и ответы; учитель видит данные назначенного ученика. Старые ссылки остаются рабочими. Все изменения подтверждены браузерными и доступовыми тестами.
